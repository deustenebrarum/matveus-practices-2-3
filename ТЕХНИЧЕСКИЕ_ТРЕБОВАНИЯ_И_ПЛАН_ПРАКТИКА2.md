### 3.1. Развернутое обоснование выбора Critter Stack и модульного монолита (для отчета)
В теоретической и практической главах отчета (разделы 1.2 и 2.1) **в обязательном порядке аргументировать** выбор данного стека:
1. **Почему Modular Monolith, а не распределенные микросервисы:**
   - Микросервисная архитектура для интернет-магазина создает избыточную сетевую задержку, сложность двухфазных коммитов и оверхед развертывания.
   - Модульный монолит объединяет изоляцию бизнес-доменов (модули `Catalog`, `Orders`, `Inventory` с собственными схемами данных) и простоту единого процесса развертывания.
2. **Почему Wolverine вместо традиционного MediatR:**
   - Wolverine устраняет шаблонный код (boilerplate): обработчики сообщений являются простыми классами без жестких интерфейсов, код диспатчинга генерируется во время компиляции.
   - Встроенный Transactional Outbox гарантирует надежную доставку межмодульных событий (`OrderCreatedEvent` $\rightarrow$ списание остатка в модуле `Inventory`) в рамках одной транзакции с базой.
3. **Почему Marten вместо классического EF Core:**
   - Модель настольного варгейма (миниатюры с десятками параметров: оружие, опции сборки, правила отрядов, фракции) идеально ложится на документную модель PostgreSQL (JSONB), исключая громоздкие реляционные таблицы связей и проблемы N+1.
   - Marten предоставляет высокопроизводительные скомпилированные запросы (`CompiledQuery`), управление схемами через Weasel и встроенный механизм версионирования документов для защиты от гонок остатков.
4. **Почему Alba + Testcontainers вместо SQLite in-memory:**
   - SQLite не поддерживает JSONB-операторы PostgreSQL, последовательности и механизмы конкурентности Marten. Использование SQLite приводило бы к ложноположительным тестам и расхождению схем (Schema Drift).
   - Testcontainers поднимает реальный образ PostgreSQL в Docker на время тестов, гарантируя полное соответствие боевому окружению.
   - Alba позволяет выполнять декларативные проверки HTTP API без поднятия сетевых сокетов, работая в 5-10 раз быстрее стандартных связок.
5. **Почему Shouldly вместо FluentAssertions:**
   - Изменение лицензионной политики FluentAssertions в сторону коммерциализации делает библиотеку рискованной для индустриальных проектов. Shouldly полностью открыта (Apache 2.0) и генерирует наглядные diff-выводы при падении тестов.

> [!IMPORTANT]
> **Разграничение с Практикой 3:**
> Testcontainers используется исключительно как инструмент разработчика для автоматизации запуска тестов в изолированном окружении, в ПМ.02 его учитывать не нужно. Промышленное развертывание, production docker-compose, Nginx, CI/CD, метрики и WAF относятся строго к ПМ.03.

### 4.2. Интеграция, отладка, тестирование и рефакторинг (Глава 2)
1. **Интеграция модулей:**
   - Техническое обоснование выбора C# 14, Critter Stack (Wolverine, Marten, Alba), Shouldly и Svelte 5.
   - Разработка вертикальных срезов (Vertical Slices):
     - Модуль каталога (`CatalogModule`): документная схема миниатюр, полнотекстовый поиск по тегам фракций, фильтрация.
     - Модуль заказов (`OrdersModule`): валидация через FluentValidation, обработчик создания заказа, расчет скидок на бандлы.
     - Модуль склада (`InventoryModule`): обработка событий через Transactional Outbox, учет единиц моделей.
     - Клиентский интерфейс на Svelte 5: компоненты витрины, корзины и карточек товаров на рунах `$state` и `$derived`.
2. **Отладка программных модулей:**
   - Единый системный алгоритм поиска и устранения дефектов.
   - Разбор **трех реальных сложных багов** (с листингами ДО и ПОСЛЕ):
     - *Баг 1 (Backend/Marten):* Ошибка полиморфной сериализации вложений wargear-опций миниатюр в JSONB (Решение: регистрация полиморфных типов документов в конфигурации Marten и использование типизированных проекций).
     - *Баг 2 (Frontend/Svelte 5):* Нарушение реактивного пересчета стоимости корзины при мутации вложенного массива позиций (Решение: перевод управления состоянием на руны `$state` и `$derived`).
     - *Баг 3 (Concurrency/Склад):* Конкурентная гонка при одновременной покупке последней миниатюры (Решение: реализация оптимистической блокировки через версионирование документов Marten `Version` и автоматический повтор через Wolverine Retry Policy).
3. **Разработка тестов и покрытие:**
   - Пирамида тестирования: модульные тесты xUnit + Shouldly, интеграционные тесты эндпоинтов через Alba + Testcontainers (PostgreSQL).
   - Тестирование валидатора заказа, проверка расчета скидки на стартовый набор Warhammer, проверка списания остатка в контейнере PostgreSQL.
   - Запуск Coverlet и подтверждение покрытия кода более **92%**.
4. **Инспектирование кода и рефакторинг:**
   - Стратегия рефакторинга и листинги **«ДО»** и **«ПОСЛЕ»**:
     - *Рефакторинг 1:* Устранение "Fat Controller" — переход от монолитного ASP.NET контроллера к изолированным Wolverine HTTP Handlers с middleware валидации.
     - *Рефакторинг 2:* Оптимизация запросов к данным — замена тяжелых ad-hoc запросов Marten на скомпилированные запросы (`CompiledQuery`) с индексацией JSONB по фракциям.
     - *Рефакторинг 3:* Рефакторинг клиента — разбиение монолитного Svelte-компонента витрины на атомарные типизированные компоненты (`MiniatureCard`, `CartDrawer`, `FactionBadge`).
